# Project Lessons Learned

## Client Disconnect Detection
- **Response close needs transport confirmation**: Fastify may mark `req.raw.destroyed` after parsing a complete body, while a response `close` event can occur with a still-live socket. Attach response listeners before upstream work so fetches and retry delays are cancellable, but abort only when the response/socket is actually destroyed (or both socket directions are closed). Normalize concurrent provider failures to the client-abort error shape once that signal fires.
- **Every SSE wrapper needs a `cancel()`, not just a read loop**: `createSSEStreamReader` — used by ~12 providers including the `claude-auth` → Anthropic chain — built its `ReadableStream` with only `start()`. A client disconnect therefore terminated the *wrapper* while the upstream reader kept pulling from the provider socket, so the request ran on against a dead consumer. A wrapper that holds an upstream reader must expose `cancel()` that cancels it, and the read loop must check a `cancelled` flag so teardown is not re-reported as a stream failure (erroring an already-terminated controller throws). This is the same defect class as the Cursor SDK cancel propagation, and it hides well: a wrapper with no `cancel()` looks correct in every happy-path test. Guarded by `stream.upstream-terminated.ts`.
- **`TypeError: terminated` is undici's mid-stream socket close, and it must be re-tagged**: when a provider closes the TCP connection after headers (seen against `api.anthropic.com`: 200 + `text/event-stream`, then `UND_ERR_SOCKET` / "other side closed" ~2 KB in), undici raises a bare `TypeError: terminated` whose real cause is nested. Propagated as-is it reaches the client as `{"message":"terminated"}` — indistinguishable from a client-side abort — and `isProviderNetworkError` never sees the code because it lives on `.cause`. Normalize at the wrapper boundary into an error carrying `code: "provider_network_error"` and the original as `cause`, so fallback/retry can classify it and the client gets a message naming the upstream. Diagnosing this needs care: `error.log` timestamps are UTC while container logs are local, and grepping a request log for the error string yields false hits when the stack trace was pasted into a conversation being logged.

## Git & Workflow
- **Cherry-picking for Integration**: When merging a feature branch from a divergent fork into a base repo with critical fixes, cherry-picking specific commits is preferred over `git merge` to avoid regression and maintain a linear history.

## LLM Provider Integration (Antigravity)
- **Auth transformer only**: Wire format is Gemini `generateContent` inside `{ project, model, request, userAgent, requestId }`. Chain `[["gemini", { cachedContent: false, thoughtSignatureFallback: "skip" }], "antigravity-auth"]`.
- **SSE re-frame must use blank-line delimiters**: Antigravity streams content in an early `data:` event, then a final event with `thoughtSignature` + empty `text`. Unwrapping via `encodeSSELine` (single `\n`) makes the next `SSEParserTransform` overwrite `currentEvent.data` and drop the content event — Claude Code sees only `(no content)`. Use `encodeSSEData` (`data: …\n\n`).
- **Dual stream dialects in Gemini transform**: Public Gemini is think→sig→text (or think→buffer text→sig flush). Antigravity is text then signature trailer. `ThinkingSequencer` + within-chunk order (thinking → text → signature) must support both; never emit late thinking after content.
- **Function-call thought signatures**: Gemini 3 / Antigravity 400 with *"Function call is missing a thought_signature in functionCall parts"* when replaying tools without the signature. Upstream puts `thoughtSignature` as a **sibling field on the same part** as `functionCall`. Keep that on the Gemini/Antigravity Unified path only; do **not** add `thought_signature` to Anthropic `tool_use` (Claude Code send/receive and `claude-auth` / `buildAnthropicBody` stay unchanged). Because Anthropic `tool_use` cannot carry the field, the signature would be lost at the client, so CCR **caches it** (`thought-signature-cache.ts`) under the tool-call id — the one identifier that survives `functionCall.id` → `tool_use.id` → `tool_result.tool_use_id` → `tool_calls[].id` — and restores it on replay, per call, including parallel siblings. Entries are scoped by **provider name** (`signatureScope`, plumbed from `provider.name` on both the request and the response side; response transformers now receive `provider` in their context): a signature is only valid at the upstream that minted it, so a session re-routed mid-conversation misses and degrades to the sentinel instead of replaying a foreign signature. Only a genuine miss stamps `skip_thought_signature_validator` on the first functionCall.
- **The sentinel is not free — discarding real signatures degrades the model until it emits broken calls**: Google's warning that the sentinel "will negatively impact model performance" is literal. In a captured multi-tool session every replayed call carried the sentinel; upstream's own signatures decayed from ~1.2 KB to a 56-byte stub over six consecutive calls, and the next turn came back `MALFORMED_FUNCTION_CALL` / "Function call is empty - no input to parse" — the model, repeatedly handed its own past tool calls stripped of the signed reasoning that produced them, stopped producing valid ones. Restoring the cached signatures is the fix; the abnormal-finish notice below is only the backstop for when it still happens. Replaying that captured session restores 19/19 signatures byte-exact with zero sentinel fallbacks. Guarded by `gemini.thought-signature-roundtrip.ts`. `enhancetool` still rebuilds streamed tool_calls without signatures — same as before; Antigravity should not rely on it for signature fidelity.
- **Sentinel scope is narrow, by spec**: Google's thought-signature docs validate only the *first* `functionCall` part of each step, explicitly do **not** validate signatures on non-functionCall parts, and call the sentinel a last resort that "will negatively impact model performance". So: never put it on a synthetic `thought: true` part, never copy a turn-level signature onto sibling parallel calls (each signature must be replayed exactly where the model returned it), and keep `ccr_…` placeholders out of the request entirely. Vertex deployments have been reported to reject the sentinel — `["gemini"|"vertex-gemini", { thoughtSignatureFallback: "none" }]` turns it off. Guarded by `gemini.function-call-signatures.ts`.
- **Tool turns must finish with `tool_use`, not `end_turn`**: Gemini/Antigravity finish functionCall streams with `STOP`. Map those chunks to Unified `finish_reason: "tool_calls"` (Anthropic `stop_reason: tool_use`). Also: never invent text/thinking `"(no content)"` placeholders on tool turns — they pollute Claude Code history and the model starts echoing them as empty final answers. Stripping that placeholder from replayed history is scoped to **model-role** turns; user and tool text is replayed verbatim, since only CCR generates the placeholder. The placeholder guard must be **stream-scoped, not chunk-scoped**: Antigravity often splits a tool turn into a `functionCall` chunk plus a bare `text: ""` + `STOP` trailer, and the trailer on its own satisfies a per-chunk `tool_calls.length === 0` test (`acknowledgeSignature()` leaves `needsContentPlaceholder` true for the rest of the stream) — so it emitted `(no content)` *after* `tool_use`, which is illegal Anthropic block order. Gate on `toolCallIndex >= 0` (already the stream's "tools emitted" state — no new flag). That trailer is also the **only** finish-bearing chunk on this dialect (the tool chunk carries `finish_reason: null`), so map it to `tool_calls` rather than dropping it, instead of relying on the Anthropic `stop_reason` safety net alone.
- **Abnormal finish reasons must not read as a finished turn**: Google returns `MALFORMED_FUNCTION_CALL` ("Function call is empty - no input to parse"), `MAX_TOKENS`, `SAFETY`, `OTHER`… CCR lowercased them straight into Unified, where Anthropic's `stopReasonMapping` knows only `stop|length|tool_calls|content_filter` and defaults everything else to **`end_turn`** — so a turn that streamed only thinking and then failed arrived as a silent, *successful* turn (the user sees nothing and has to type "so?"), and a `MAX_TOKENS` truncation was indistinguishable from a complete answer. Normalize with `normalizeGoogleFinishReason` (`MAX_TOKENS`→`length`, safety family→`content_filter`) and, when an abnormal finish leaves **no text and no tool calls**, emit `buildAbnormalFinishNotice` — the reason plus upstream `finishMessage` — instead of `(no content)`. Suppress the notice once tools were emitted (text after `tool_use` is illegal block order; the tool loop carries the turn). The notice is CCR-generated, so `buildRequestBody` strips it from replayed **model** turns exactly like `(no content)`. Guarded by `gemini.abnormal-finish.ts`.
- **Effort is Claude Code's call, not the slug's**: Claude Code sends `thinking: {type:"adaptive", display:"summarized"}` plus `output_config: {effort:"high"}` and **no `budget_tokens`** (verified in `~/.claude-code-router/logs`), so `reasoning.effort` is the only effort signal on this path. `gemini-thinking.ts` translates it per family and the model id is **never rewritten** — a configured `gemini-3-pro-low` keeps talking to `gemini-3-pro-low`; tier-suffixed ids accept their family's whole level set, so the suffix only selects the upstream quota bucket. Antigravity's `*-tiered` ids are the entries designed for per-request tier selection. Dialects must never be mixed (`thinkingLevel` + `thinkingBudget` in one request is a documented 400): Gemini 3+ uses levels (3-Pro `low|high`; later Pro minors add `medium`; Flash/Lite add `minimal`), Gemini 2.5 and Claude-via-Antigravity use `thinkingBudget` (Claude's floor is 1024 — drop the config rather than go under). Clamp *up* so `medium` on 3-Pro and Claude/CCR's `xhigh`/`max`/`ultra` become `high` instead of degrading. `includeThoughts: true` must be set whenever thinking is on, even with no effort, or Antigravity streams no thought parts at all.
- **Claude-on-Antigravity rejects typeless unions in tool schemas**: Antigravity parses our Gemini body into the Gemini Schema proto and re-emits it for Anthropic, so a subschema with `anyOf` and **no sibling `type`** comes out invalid — `tools.N.custom.input_schema: JSON schema is invalid. It must match JSON Schema draft 2020-12`. Claude Code's own `SendMessage` tool (index 18) has that exact shape, so every session with the standard tool set failed. Live probing pinned it: flat schema → 200; typeless `anyOf` → 400; `anyOf` **with** a `type` → 500 *"type and anyOf cannot be both populated"* (so adding a type is not a fix); nested `anyOf` → 400. `collapseTypelessUnions` folds the union onto its first typed branch and lists the dropped ones in the description. Gate it on `claude-*` only — Gemini accepts typeless unions, and uppercase Gemini types (`OBJECT`/`STRING`) are fine for the Claude backend, so the rest of the transform stays shared. Guarded by `antigravity.claude-tool-schema.ts`.
- **`functionResponse.id` is required (especially for Claude-on-Antigravity)**: We always set `functionCall.id` from the Unified `tool_calls[].id`, but historically omitted `id` on the paired `functionResponse`. Native Gemini often tolerates name-only matching for a single call; Antigravity's Claude backend remaps Gemini → Anthropic and then requires `tool_result.tool_use_id`, so a missing response id surfaces as `messages.N.content.0.tool_result.tool_use_id: Field required`. Gemini's own parallel-tool docs also say each `functionResponse` must carry the matching call `id`. `buildRequestBody` now prepares call ids once and stamps the same value on both parts. Guarded by `gemini.function-call-signatures.ts` / `gemini.dual-dialect-request.ts`.
- **No cachedContents**: Antigravity has no `cachedContents` resource; set `["gemini", { cachedContent: false, … }]` (user config often omits this and logs 404s).
- **Strict protobuf JSON**: Prefer camelCase protocol keys (`generationConfig`, `thoughtSignature`, `mimeType`). Snake_case that the public API tolerates can 400 on `v1internal`.
- **Project id**: Comes from `POST /v1internal:loadCodeAssist` → `cloudaicompanionProject` (string or `{id}`). Metadata must use `platform: "PLATFORM_UNSPECIFIED"` — `MACOS`/`WINDOWS` are invalid enum values and return 400, so discovery silently failed. Free-tier accounts already have a managed project; `onboardUser` is only needed when load returns none. Cache into `antigravity_auth.json`. Never hardcode a third-party default. Optional for chat; required for `fetchAvailableModels`.
- **OAuth callback**: Redirect is pinned to `localhost:51121`; CCR Fastify serves public `/oauth-callback` (compose maps `51121:3456`). Use `--manual` when the callback cannot reach the server.
- **Endpoint order**: generateContent prefers daily → autopush → prod; loadCodeAssist prefers prod first.
- **Endpoint fallback rules** (a transient daily failure surfaced as a bogus 500 about a *staging* API): only **transport** errors may move to the next host — `isProviderNetworkError`, never a client abort (re-sending an abandoned prompt to two more hosts) and never an error we raised ourselves. The sandbox hosts answer **403 SERVICE_DISABLED** when the account's project is not entitled to that deployment, so 403 must keep walking (prod is last) and the host gets marked unusable for the session instead of being re-probed. When the walk runs out, throw `createApiError` with the upstream status: returning a non-ok body lets `convertOpenAIResponseToAnthropic` fail on the missing `choices` and report an opaque **500** with Google's error text embedded. Guarded by `antigravity.endpoint-fallback.ts`.

## LLM Provider Integration (Gemini)
- **Problem**: Gemini 500 errors and tool use failures in multi-turn conversations.
  - **Resolution**: Implemented robust error handling and enhanced state management within the Gemini transformer. This ensures conversation history is correctly maintained and API calls are resilient to transient issues, preventing server errors and enabling reliable tool execution across multiple turns.
  - **Symptoms & Fix**: If Gemini returns 500 errors or tool calls fail in multi-turn dialogues, review the conversation state management and message history preparation for the Gemini API. Look for issues in how previous turns are summarized or passed, and ensure error handling (e.g., retries) is active.
- **Problem**: Gemini/Gemma streaming issues, autocompact malfunctions, and tool schema validation failures.
  - **Resolution**: Improved the streaming parser/serializer to correctly handle partial and complete stream events for both Gemini and Gemma. Enhanced autocompact logic to intelligently manage the context window, preventing unexpected truncations. Strengthened tool schema sanitization to ensure generated tool definitions strictly comply with API requirements.
  - **Symptoms & Fix**: If streaming responses are incomplete or corrupted, autocompact causes unexpected message shortening, or tool definitions are rejected, inspect the respective streaming, context management, and schema validation components of the Gemini/Gemma integration. Verify JSON schema conformity and stream processing integrity.
- **Problem**: Inefficient message grouping and suboptimal streaming logic for Gemini tool call handling.
  - **Resolution**: Refactored and optimized the internal message grouping mechanism and streaming logic for Gemini. This involved implementing smarter buffering and assembly of partial tool call events, leading to more efficient processing and faster, more accurate tool invocation.
  - **Symptoms & Fix**: If Gemini tool calls are delayed, appear out of order, or are incorrectly interpreted during streaming, examine the message grouping and streaming pipeline. Confirm that partial tool call payloads are being correctly identified, buffered, and reassembled before dispatching the full tool call.
- **Problem**: Gemini thinking-stream refactors can preserve happy-path parity but still lose metadata or raise cleanup exceptions on abrupt stream termination.
  - **Resolution**: Keep the last successfully parsed chunk/candidate around for end-of-stream finalization, and harden shared stream cleanup so `onComplete` failures and `controller.close()` do not mask the original stream error.
  - **Symptoms & Fix**: If fallback thinking/content chunks are missing `id` or `model`, or stream failures produce noisy secondary exceptions during shutdown, inspect the finalization path and the shared SSE reader cleanup order before changing the thinking sequencer logic.

## LLM Provider Integration (Mistral)
- **Parameter Mapping**: Mistral requires `reasoning_effort` (low, medium, high) instead of a `reasoning` object. 
- **Model ID Wildcards**: Use `.startsWith()` for model families (e.g., `mistral-small-`) to support multiple versions of the same model without manual list updates.
- **Effort Heuristics**: Mapping `max_tokens` to effort levels (low < 1k, medium < 5k, high > 5k) is a reliable way to translate unified reasoning requests to provider-specific efforts.
- **Nested Thinking Format**: Some Mistral models return thinking as an array of blocks within the `content` field (`delta.content = [{ type: "thinking", thinking: [...] }]`). Naive string concatenation of these objects results in `[object Object]` in the UI.
- **Aggressive Serialization**: To prevent `[object Object]` outputs, always verify if thinking content is a string or an object. Use a fallback to `.text` property or `JSON.stringify()` when dealing with provider-specific thinking blocks.

## LLM Provider Integration (DeepSeek)
- **Reasoning Replay Is Mandatory**: When DeepSeek thinking mode remains enabled across tool-use turns, prior assistant tool-call messages must carry their original `reasoning_content` back to the API. Replaying only the tool calls and visible assistant text is not enough.
- **Repair Source Order**: The safest replay order is: keep existing `reasoning_content` if present, otherwise derive it from `thinking.content`, otherwise restore it from a local cache keyed by conversation scope plus tool-call identity/signature.
- **Cache Population Point**: Populate the cache from provider responses, not from user-facing display chunks alone. For streamed responses, accumulate reasoning text plus the eventual assistant content/tool calls and store the final assistant message shape on stream completion.
- **LiteLLM `_sanitize_empty_text_content` Placeholder (DeepSeek via `anthropic/` prefix)**: When routing Codex → LiteLLM (`anthropic/` prefix) → CCR → DeepSeek, the placeholder `[System: Empty message content sanitised to satisfy protocol]` can appear in responses. The root cause: Codex sends tool-call-only assistant turns as `{"type": "message", "role": "assistant", "content": [{"type": "output_text", "text": ""}]}` via the Responses API. LiteLLM's Responses→Chat conversion produces an assistant message with an empty text block and no `tool_calls` field, which bypasses the original `tool_calls` guard and triggers the placeholder replacement.
  - **Fix (factory.py)**: In `litellm/litellm_core_utils/prompt_templates/factory.py::_sanitize_empty_text_content`, the role gate `not in ["user", "assistant"]` is changed to `!= "user"`. The Anthropic conversion loop (`anthropic_messages_pt`) already drops empty text blocks for assistant messages — the placeholder was redundant.
  - **Fix (transformation.py)**: In `litellm/responses/litellm_completion_transformation/transformation.py`, the message conversion skips empty text blocks during Responses API → Anthropic format conversion, preventing them from reaching the sanitization layer.
  - **Patched files**: `litellm-patch/factory.py`, `litellm-patch/transformation.py` (BerriAI/litellm on GitHub)
  - **Mount**: Volume-mount over the installed paths in the LiteLLM container (paths depend on Python venv). Restart only — no rebuild needed.
- **LiteLLM `parse_tool_call_arguments` Unterminated JSON / Raw Newlines**: When routing Codex → LiteLLM (`anthropic/` prefix) → Anthropic API, tool call arguments containing long shell heredocs (e.g., `exec_command` writing JS files) can get truncated mid-string during transmission. The original `_attempt_json_repair` correctly tracked string state but refused to repair when `in_string` was `True` (returned `None` when `opener_stack` was empty). Raw newlines from CLI heredocs were never handled at all.

## Architecture
- **Reasoning effort needs one canonical off state and protocol-boundary mappings**: Chat Completions sends top-level `reasoning_effort`, Responses sends `reasoning.effort`, and Anthropic sends `output_config.effort`; carrying those wire shapes directly through Unified loses values on cross-protocol routes and lets `none` look truthy. Normalize every inbound value to `reasoning: { effort, enabled }`, with `none` always setting `enabled: false`, and make routing/provider helpers honor the explicit off state before checking for any effort string. Serialize at the destination boundary: Chat uses `reasoning_effort`, Responses uses `reasoning.effort`, and Anthropic disables thinking for `none`, maps `minimal` to `low`, and maps the CCR/OpenAI `ultra` extension to Anthropic's `max`. Guard the contract with a full inbound/outbound effort matrix, not a single `high` fixture.
- **Behavioral parity with Claude Code is the goal, not lower usage**: When CCR presents third-party agent traffic as Claude Code for subscription OAuth, success means Anthropic applies the same identity, capabilities, context window, and account usage policy as it would to the equivalent direct Claude Code request. Do not add per-request token preflights, suppress `[1m]` betas, impose a 200K cap, force an API-key lane, or block credit-consuming models merely to reduce usage unless the user separately asks for that policy. The current 2.1.226 decompilation shows the normal Messages path does not add a count-tokens preflight; preserve upstream long-context/quota errors for Anthropic clients so Claude Code can classify them itself.
- **Inbound protocol state belongs to the request, not a transformer-call context**: endpoint normalization and response conversion receive different context objects. Per-turn data needed in both directions (for example Responses `call_id` mappings and the caller's original model) must live on `req.protocolContext`; storing it only on the temporary request-transform context silently loses it before the response stage.
- **Every provider attempt gets its own Unified body**: provider transformers are allowed to mutate requests in place (`messages` → Responses `input` is one example). Clone the normalized request separately for the primary and each fallback, or a failed first attempt can leave the fallback with the wrong wire shape.
- **Exact-wire passthrough sends the *adapted* client body, not `req.body`**: routing used to mutate `req.body` in place, so subagent-tag removal and `REWRITE_SYSTEM_PROMPT` reached the upstream for free. Once normalization moved to a clone, the passthrough path kept sourcing the untouched original and silently leaked `<CCR-SUBAGENT-MODEL>` upstream while dropping the rewritten prompt. `PreparedInboundRequest` therefore carries both: `originalBody` (immutable, for legacy Anthropic custom routers) and `clientWireBody` (adapted, what passthrough must send). The Claude Code billing marker at `system[0]` is deliberately *not* stripped — removing it is exactly the kind of divergence that identifies the request as proxied.
- **The upstream URL must be resolved after `transformer.auth()`, not before**: `auth()` is the stage that knows the protocol-correct path — Anthropic derives `/v1/messages?beta=true` from a bare provider origin. Snapshotting `config.url || provider.baseUrl` above the auth block makes `auth.config.url` dead code, and a provider configured with an origin-only `api_base_url` POSTs to `/`.
- **Anthropic cache fidelity is client- and destination-scoped**: native Desktop/CLI requests use the raw Anthropic body and preserve the client's own breakpoints; `other` clients routed to an in-scope Anthropic provider use the pinned Claude Code 2.1.226 profile (uncached billing block, cacheable system blocks, one eligible message-tail breakpoint); all other destinations receive no Claude cache/system synthesis. `applyRawAnthropicPromptCaching` remains reserved for provider adapters that explicitly need generic cross-protocol breakpoints, never as a universal normalizer for native or emulated Claude traffic.
- **Current Claude Desktop 3P is a Desktop-hosted Agent SDK/CLI transport**: Desktop 1.26832.0 sets `CLAUDE_CODE_ENTRYPOINT=claude-desktop-3p` and bundles Agent SDK 0.3.222 with Claude Code 2.1.222, producing a CLI-shaped UA such as `claude-cli/2.1.222 (external, claude-desktop-3p, agent-sdk/0.3.222)`. Classify the complete native fingerprint as `claude_desktop` before the generic CLI branch; incomplete lookalikes still fail closed. Preserve its bundled versions, application headers, body and client-authored cache markers exactly instead of substituting the separately pinned third-party emulation profile.
- **Exact-wire passthrough is still a credential boundary**: never copy the inbound header map upstream. Preserve only an allowlist of protocol/SDK metadata, then generate provider authentication independently. Denylists are insufficient because arbitrary headers can themselves be tenant credentials.
- **Responses completion waits for transport termination**: Chat providers may send `finish_reason` and then a separate `choices: []` usage chunk. Record the finish reason, but emit `response.completed` only at `[DONE]` or normal upstream close. Every Responses event needs a monotonic `sequence_number`, and output indices must be allocated once per item so a later text delta cannot renumber an earlier tool call.
- **Thin Transformer Pattern**: For maintainability, keep transformer classes as thin wrappers that handle high-level provider config and delegate all data transformation logic to a dedicated utility file (e.g., `gemini.util.ts`, `mistral.util.ts`).
- **Provider-native caching translation**: CCR should treat Claude Code's Anthropic request as the source protocol and translate caching into each upstream's native mechanism. Do not equate "provider does not support Anthropic `cache_control`" with "provider cannot cache"; use OpenAI prompt cache fields, Mistral keys, Gemini cached-content resources, or stateful SDK/browser sessions as appropriate.
- **OpenAI-compatible is not OpenAI cache-compatible**: Gate request fields by the exact provider/model contract. A generic compatible endpoint may reject `prompt_cache_key`, `prompt_cache_breakpoint`, or OpenAI cache options even though it accepts Chat Completions messages.
- **Cache observability is bidirectional**: Request translation is incomplete unless response adapters preserve native cache reads and writes through Unified usage and back to the Anthropic fields Claude Code consumes.
- **Usage subsets are disjoint, not nested**: In CCR's Unified usage, `prompt_tokens = input_tokens + cache_read + cache_creation` (see `toOpenAIUsage` in `vertex-claude.util.ts`). The inverse in `toAnthropicCacheUsage` (`anthropic.transformer.ts`) must therefore be `input_tokens = prompt_tokens − cached − written`. Dropping the `− written` (on the false assumption that `cache_write_tokens` is a subset of input) breaks the round-trip and over-reports context usage. `cache-paths.integration.ts` guards this.
- **OpenRouter Gemini requires Anthropic-format `cache_control`**: Per OpenRouter docs, Gemini caching needs `cache_control: {type:"ephemeral"}` breakpoints inserted *within message content* (same format as Anthropic; OpenRouter uses only the last breakpoint for Gemini). Route OpenRouter Gemini through `applyQwenPromptCaching` (content-level marker), NOT strip and NOT `applyRawAnthropicPromptCaching` (which sets a top-level `request.cache_control` the OpenAI-shaped endpoint ignores). Stripping the markers silently disables Gemini prompt caching.
- **`endPoint` is an instance field, never on the prototype**: Transformers declare `endPoint = "/…"` as a class field, so `Ctor.prototype.endPoint` is always `undefined`. A transformer switched to `static TransformerName` (needed so `["gemini", opts]` can pass options) is stored as a constructor and silently loses its native route unless `getTransformersWithEndpoint` instantiates it. Registration also has to dedupe by endpoint — `openai` and `vercel` both declare `/v1/chat/completions`, and Fastify aborts boot with `FST_ERR_DUPLICATED_ROUTE`. Guarded by `transformer-service.endpoints.ts`.
- **Anthropic stream state is shared by every provider**: `anthropic.transformer.ts` is the single exit stage, so its block bookkeeping must survive any interleaving. Closing a block on a text delta has to clear `isThinkingStarted` (else a thinking → text → thinking provider streams `thinking_delta` against the text block index and Claude Code drops the turn). Opening `tool_use` must clear both `hasTextContentStarted` and `isThinkingStarted` — leaving the former sticky makes a later `text_delta` land on the tool_use index and Claude Code drops the turn with "Content block is not a text block". `currentContentBlockIndex` is the *only* handle on the open block, so a path that opens and closes its own blocks (the annotations loop) must not clear it: doing so strands whatever it interrupted, and since every close path is gated on `>= 0`, that block is never closed at all. The close before annotations stays limited to text blocks on purpose — a `tool_use` may still be streaming argument JSON, and closing it early emits `input_json_delta` after `content_block_stop`, which is worse than a late close. The `tool_use` stop-reason safety net must key on tool_use blocks actually emitted, not on `delta.tool_calls` chunk counts — `tool_calls: []` is truthy and would promise a tool call that never arrives. The non-streaming reply must use the same block order as the stream and as `buildAnthropicBody` — thinking → server tool use → text → tool_use — since a trailing thinking block does not lead the assistant turn when a client replays it. Guarded by `anthropic.stream-boundaries.ts`.
- **Vercel AI Gateway: auto caching replaces manual markers**: When the Vercel transformer sets `providerOptions.gateway.caching = "auto"`, the gateway inserts its own `cache_control` breakpoints. ## LLM Provider Integration (Codex / ChatGPT Backend)
- **API Format**: Codex uses the Responses API (`POST /responses`) with an `input` array of message/function_call/function_call_output entries, not the standard `messages` array. System messages become a top-level `instructions` string — use Claude Code's system message directly, not model-specific defaults.
- **OAuth Authentication**: Codex authenticates via OAuth PKCE, not static API keys. Tokens are stored in `~/.claude-code-router/codex_auth.json` and automatically refreshed by the transformer. The provider config still needs a placeholder `api_key` field.
- **Streaming Is Mandatory**: Codex requires `stream: true` and `store: false`. The transformer must propagate `stream: true` to the original request body via `context.req.body.stream = true` so the downstream `formatResponse` sends an SSE stream rather than JSON.
- **Cloudflare Strips Content-Type**: Codex API responses are proxied through Cloudflare, which strips the `Content-Type` header from SSE responses. The `transformResponseOut` method must treat missing/empty `Content-Type` as `text/event-stream` and default to SSE parsing before attempting JSON parsing.
- **Tool Call Conversion**: Codex emits `response.output_item.added` (function_call) for tool use start and `response.function_call_arguments.delta` for argument chunks. These must be converted to OpenAI-format tool call chunks (`choice.delta.tool_calls`) which the AnthropicTransformer then converts to Anthropic-format `content_block_start`/`content_block_delta` events.
- **Multiple Thinking Waves**: Codex can emit reasoning in multiple waves (thinking content → signature → thinking content → signature). When the AnthropicTransformer closes a thinking block on signature, `isThinkingStarted` must be reset to `false` so each subsequent wave opens a new `content_block_start`. Without this reset, the second wave gets `content_block_delta` with index `-1`, causing Claude Code's "Content block not found" error.
- **`encrypted_content` is ciphertext, not an item id**: Codex/OpenAI verify `reasoning.encrypted_content` on replay. Storing a Responses reasoning `item_id` (`rs_…`) in Unified `thinking.signature` and later copying it into `encrypted_content` (or minting `rs_${Date.now()}`) produces `invalid_encrypted_content` / "Encrypted content could not be decrypted or parsed." Keep three fields separate on Unified thinking: `signature` (Anthropic/Gemini), `encrypted_content` (provider-minted ciphertext only), and `id` (Responses `rs_…`). Heal poisoned history where `signature` is already an `rs_*` id; omit Anthropic/Chat signatures as Codex ciphertext; only emit a reasoning item when there is content, real ciphertext, or a thinking-carried id — never from a fallback id alone. Guarded by `openai.inbound-responses.ts`.

## LLM Provider Integration (Gemini Nano / Chrome Prompt API)

- **Context Window**: Gemini Nano has a ~9216 token context window. These constraints require aggressive prompt compression and structured output enforcement.
- **Persistent Session Architecture**: The bridge maintains a single `LanguageModel` session across all requests. Conversation history is carried forward within the session itself — no need to rebuild from `initialPrompts` each turn. This preserves context naturally but requires tracking `processedMsgCount` to only feed new messages to the model.
- **Structured Output via responseConstraint**: The model has no native function calling. Instead, `responseConstraint` (JSON Schema, Chrome 137+) forces output to match `{"tool_calls": [{"name": "...", "arguments": {...}}]}`. The schema enforces `maxItems: 1` on `tool_calls` to keep output within budget. Text responses are emitted as a tool call to the `ExitTool`.
- **Whitespace Stalling**: Gemini Nano stalls on whitespace-heavy content (Python code indentation, JSON formatting). The bridge detects this with a whitespace character counter and aborts the stream after 2000 consecutive whitespace chars with no content. Write calls are limited to 3 lines — files are built incrementally with Write→Edit→Edit chains.
- **System Prompt Compression**: Claude Code's system prompt (~2400 chars of verbose instructions) is replaced with a compact ~700 char prompt listing 5 core tools (Bash, Read, Write, Edit, ExitTool) with concise parameter descriptions and format examples. This reduction is critical to avoid overwhelming the model and to keep the prompt within the tight context budget. XML-style tags (`<tools>`, `<format>`, `<rules>`) provide clear structure as recommended by Gemini prompting docs.
- **Context Budget Conservation & Tool Filtering**: `stripClaudeCodeContext()` removes `<system-reminder>`, `<command-*>`, and `<local-command-*>` blocks injected by Claude Code. 
  - **Reasoning**: Tool results and file contents are passed through without arbitrary truncation, but the verbose MCP-injected instructions in `<system-reminder>` and unsupported tools (e.g., WebSearch, AskUserQuestion) would quickly exhaust the ~9K token window.
  - **Correction**: `<system-reminder>` blocks containing tool calls ("Called the ... tool") or tool results ("Result of calling the ... tool") MUST be preserved and transformed into structured `<tool_result>` blocks. Simply stripping them removes critical tool output that Claude Code expects the model to see.
  - **Caveats**: This is a destructive filter; the model is physically unable to use any tools outside the core 5, even if requested. The implementation must carefully remove orphaned tags to prevent the model from seeing fragmented tool-call patterns that could trigger formatting hallucinations. Continuation prompts are avoided in favor of raw tool results labeled as "Tool Result:".
- **Assistant Message Inclusion on First Turn**: When `processedMsgCount === 0` (first turn or session rebuild), assistant messages MUST be included in `buildTurnPrompt` so the model sees its own prior tool calls. Without this, the model receives `<tool_result>` blocks with no context about having called those tools, triggering reflexive re-calls. Subsequent turns skip assistant messages since the Prompt API session already has them in context.
- **Multi-Session Architecture**: The bridge fingerprints requests by `User-Agent + IP` hash into separate `LanguageModel` sessions. Each client gets its own session with independent context, turn count, and stats. Dashboard updates must iterate ALL sessions, not just the `'cli'` default — gating `updateDashboard()` behind `if (sessionId === 'cli')` means fingerprinted sessions never trigger UI updates.
- **Session Reset Hygiene**: When resetting a session (`resetSession`), `lastActivityAt` must be cleared. Otherwise, the idle eviction timer sees stale timestamps and may skip eviction of dead sessions, or vice versa.
- **Mimicry & Notation**: Nano is highly prone to mimicking input notation. If the prompt contains `@filename` references, the model will likely echo `@filename` in its response. This requires explicit, high-priority prohibitions in the system prompt (e.g., `CRITICAL: NEVER use the "@" symbol to refer to files...`).
- **Reflexive Tool Loops**: When tool results are provided in the prompt, Nano may still reflexively attempt to call the tool again. A strong notice prepended to the prompt naming the exact tools already called (e.g., `[NOTICE: The assistant already called tool(s): Read. You MUST NOT call those tools again...]`) is necessary to break this loop. A generic "review results" notice is insufficient — the model needs to see the specific tool names it already invoked.
- **Read Result Extraction**: Original regex-based extraction from prompt text was fragile and often failed. Fixed by using structured message matching: track `tool_call_id` from Read tool calls in assistant messages, then match against `tool_call_id` in tool result messages. Both OpenAI format (`role: "tool"`, `tool_call_id`) and Anthropic format (`tool_result` content blocks in user messages) are supported.
- **Auto-Compaction**: Triggers at 85% context usage (`usageRatio >= 0.85`). Calls `resetSession()` which destroys the old session and creates a new one with system prompt + "[Earlier conversation compacted to save context.]" appended. All messages are marked as processed to avoid re-feeding.
- **Retry on Broken Output & Stalling**: If the model produces invalid JSON or stalls on whitespace-heavy content (emits 1000+ whitespace chars with no content), a second attempt is made. If it stalled, the retry occurs without the `responseConstraint` and with a dynamic temperature increase (e.g., +50%) to break deterministic loops. If it was just malformed JSON, a formatting correction is appended.
- **Hallucination Prevention**: Added an "OPERATIONAL OVERRIDE" and strict guidelines in the system prompt to prevent the model from inventing file paths (e.g., `/tmp/my_file.txt`) and force it to use EXACT values from the user's request.
- **Tool Result Labeling**: Tool outputs are explicitly labeled as "Tool Result:" in the turn prompt, and the model is instructed to check for these existing results before initiating new tool calls.
- **Parameter Clamping**: Session creation now automatically clamps `temperature` and `topK` to the model's supported limits (`maxTemperature`, `maxTopK`) to avoid API creation failures.
- **Bridge Endpoints**: The bridge exposes `GET /v1/models` (list with `display_name` and `context_window.used_percentage` for statusline), `GET /v1/models/{name}` (individual model info for Claude Code's model discovery), `POST /v1/chat/completions` (streaming/non-streaming), and `GET /health`.

## Architecture — Transformer Passthrough & Custom Header Injection
- **Problem**: When CCR needs to talk to an Anthropic-style upstream that requires custom headers (e.g., `x-opencode-*`, `x-api-key`), neither existing mode works:
  - **Bypass mode** (`use: ["Anthropic"]` only) forwards all client headers and preserves body format, but you cannot chain provider-level transformers — no custom headers can be injected.
  - **Normal mode** (multiple transformers) runs provider-level transformers but `transformRequestOut` converts the body to OpenAI format, which the Anthropic upstream rejects.
- **Resolution**: Added a per-provider `passthrough: true` config flag that decouples body format conversion from provider-level transformer execution. The flow:
  - `shouldBypassTransformers` returns `false` (multiple transformers present), so provider-level `transformRequestIn` runs and injects custom headers.
  - `skipBodyConversion` (bypass || passthrough) gates only the endpoint transformer's `transformRequestOut`/`transformResponseIn`, keeping the body in raw Anthropic format.
  - `sendRequestToProvider` also calls `transformer.auth()` in passthrough mode to inject `x-api-key`.
- **Key insight**: `bypass` gates provider-level transformers (line 238: `!bypass && provider.transformer?.use`). The fix was to introduce a separate `skipBodyConversion` flag so the endpoint transformer's body conversion is independently controllable.
- **Auth header conflict**: When `x-api-key` is injected, remove the hardcoded `Authorization: Bearer` to prevent "multiple credentials" errors on strict gateways.
- **Client header forwarding**: Exact-protocol bypass keeps only named Anthropic/OpenAI version, beta, organization/project headers plus `x-stainless-*`, content negotiation, user agent, and idempotency. CCR credentials, cookies, hop-by-hop fields, arbitrary `openai-*`/`anthropic-*` names, and other custom headers never cross the boundary. Manual `passthrough` mode sends only transformer-injected headers.
- **Config example**:
  ```jsonc
  {
    "transformer": {
      "use": ["Anthropic", "opencode-headers"],
      "passthrough": true
    }
  }
  ```
- **Transformer naming**: Use the `name` field value (e.g., `"Anthropic"`), not the class name (`"AnthropicTransformer"`), in config arrays.
- **Files modified**: `packages/core/src/api/routes.ts` (4 changes), `packages/core/src/services/provider.ts` (1 change)

## OpenCode Zen — Session-Hash Provider Routing (self-heal)
- **Root cause**: Zen picks an upstream backend by hashing the **last 4 characters** of the `x-opencode-session` header (`packages/console/app/src/routes/zen/util/handler.ts` `selectProvider`: `for i in [len-4,len) h=h*31+charCodeAt(i); index=h%providers.length`). If a conversation's session hashes to a bad slot, **every** request in that conversation fails identically — deterministic, not transient. Two signatures, both from the routing/capacity layer:
  - HTTP **401** `{"error":{"type":"ModelError","message":"No provider available"}}` — hashed slot has no provider.
  - HTTP **400** `{"error":{...,"message":"Error from provider (Console): Upstream request failed"}}` — hashed backend failed its own upstream call.
- **These are NOT auth/validation errors**: a genuine bad key is also 401 and a malformed body is also 400, so status code alone is not enough — match the exact `error.type`/`message` before treating it as recoverable. Everything else passes straight through as terminal.
- **CCR feeds the hash indirectly**: Claude Code sends `metadata.user_id` = JSON with `session_id` → `router.ts:parseSessionId` extracts it into `req.sessionId` → `opencode-headers` maps it to a stable generated `ses_…` header (random 14-char suffix, cached per conversation). Because the suffix is pinned for the conversation's lifetime, a bad initial roll dooms the whole conversation.
- **Fix = self-healing re-roll, fully contained in the transformer**: `opencode-headers.transformer.ts` owns its own upstream call via `config.__providerResponse` (same escape hatch `cursor-sdk` uses at `routes.ts:459`, which bypasses the generic `if (!response.ok) throw` at line 560). On a routing-failure signature it deletes the cached session (`invalidateSession`), regenerates a new `ses_…` (new suffix → new bucket), and retries up to 3×. On success the new session is cached, staying sticky to the good bucket (preserves Zen `x-session-affinity` caching). Any other non-ok response is re-thrown as the exact `provider_response_error` that `sendRequestToProvider` would have produced, so no opencode-specific status semantics leak into the generic path.
- **Why not `handleFallback`**: the existing fallback switches to a *different model* from config; it does not re-run the same model with a fresh session, so it can't fix a bucket dead-end.
- **When owning the fetch, you lose `sendRequestToProvider`'s Bearer/x-api-key normalization** (routes.ts:491-510) — but `opencode-headers` already sets `x-api-key` and nulls `authorization` itself, and `sendUnifiedRequest` drops falsy header values, so `authorization` never reaches the wire. Reuse `sendUnifiedRequest` (not raw `fetch`) so proxy/abort/timeout behavior stays identical; reach proxy config via `context.req.server.configService.getHttpsProxy()`.
- **Verification**: 25 distinct-session burst went 24/25 → 25/25 after adding the 400 case; container logged exactly the expected re-roll events (`status:400, attempt:1`) with 0 client-facing errors. Test: `packages/core/src/tests/opencode-headers.no-provider-retry.ts` (recover-401, recover-400, genuine-401 passthrough, genuine-400 passthrough, Zen-wrapped validation passthrough, exhaustion).
- **UA pinning**: `user-agent` must match a real published opencode version (`opencode/<ver>`, format is `opencode/${InstallationVersion}` from the client). Bumped to `1.18.4` (current npm `opencode-ai`).
- **Do not re-roll on Zen-wrapped validation 400s**: DeepSeek/SGLang rejects nameless `response_format.json_schema` with a real validation error; Zen still wraps it as `Upstream request failed: [400] … validation errors`. Matching only `/upstream request failed/i` retried the same broken body 3×. Exclude `/validation error/i` from the routing-failure classifier.
- **Anthropic → Unified json_schema must default `name`**: Claude Code's `output_config.format` often omits `name` (session title generation). OpenAI Chat Completions requires `json_schema.name`. Default to `"response"` in `AnthropicTransformer.transformRequestOut` when absent so OpenCode/NVIDIA/OpenRouter do not 400.

## LLM Provider Integration (Codex / ChatGPT Backend)

- **Model-Slug Suffixes Are Unnecessary**: Parsing effort from model name suffixes (`-high`, `-xhigh`) adds complexity for no benefit in this codebase. Effort comes from Claude Code's `/effort` setting, not from model naming conventions.
- **Active Maintenance Awareness**: Claude Code is under active development and its API request format can change (e.g., `budget_tokens` → `output_config.effort`). If a passthrough seems to work only for certain values, check the actual request body in the logs rather than assuming the mapping is correct.
- **Keep CLI and server runtime integrations self-contained**: CCR's CLI and
  server are separate components and may run concurrently. Implement equivalent
  credential or external-catalog behavior inside each component instead of
  importing one component's runtime manager/cache into the other. Coordinate
  Codex auth only through the credential-file contract and shared
  filesystem-lock convention; models.dev discovery uses independent fetch/cache
  lifecycles in `ccr codex-config` and the server's `/v1/models` route.
- **models.dev row selection must be deterministic across CLI and server**:
  match the configured model name to the catalog's exact model id. A unique row
  is authoritative; duplicate ids must resolve to the native family provider.
  Never prefer CCR's configured provider, catalog order, a row merely because
  it advertises effort, or a suffix-stripped near match. Emit the selected
  row's effort values exactly; only a true miss gets the explicit Codex fallback
  (`low`/`medium`/`high`, 200K context).
  Codex requires the `supported_reasoning_levels` field even for a matched

  deserialization.
- **Claude-safe model aliases are transport identities, not routing identities**:
  discovery must encode otherwise-filtered canonical `provider,model` ids as
  `claude-` plus lowercase UTF-8 hex. Decode and validate the alias against the
  configured route before scenario selection, then route only the canonical id;
  otherwise `Router.default` can silently replace the bare alias. Keep `[1m]`
  outside the encoded payload, preserve the original client id for response
  echoing, and accept both canonical and encoded ids at every inbound boundary.
  Gate only discovery serialization with `MODEL_ID_OUTPUT`: `literal` is the
  absent/invalid-value default, while `masked` emits aliases. Never gate the
  inbound decoder on this setting.
- **PAT detection must include configuration indirection**: A literal `at-…` is unambiguous, but Codex `api_key` may also be `$VAR`, `${VAR}`, or a bare variable name whose environment value starts with `at-`. Resolve those forms at the auth-selection boundary in both core/runtime and CLI discovery; do not discard unresolved references in generic API-key helpers before the Codex resolver sees them. Only a resolved `at-` token selects PAT—placeholders such as `oauth` still select OAuth.
- **Whoami API for PAT**: `GET https://auth.openai.com/api/accounts/v1/user-auth-credential/whoami` with `Authorization: Bearer <pat>`. Match Codex by validating account, user, and plan metadata and retaining the FedRAMP flag.

- **PAT lookup lifetime**: Deduplicate concurrent `/whoami` calls and use a
  bounded metadata cache. Invalidate it after a PAT 401, but do not retry an

- **Auth selection is not fallback recovery**: An `at-` config value selects
  PAT mode; a non-PAT placeholder selects OAuth. Once selected, an auth failure

  `https://api.openai.com/auth.chatgpt_account_id` and
  `chatgpt_account_is_fedramp`, then persist the selected account.

## LLM Provider Integration (Qwen Chat)
- **Single-JWT Auth Model**: Qwen has no public OAuth flow. Users copy a JWT from `localStorage.getItem('token')` at `chat.qwen.ai` (after signing in) and paste it into the CCR auth page. The token is one long-lived credential — no `refresh_token` field, no PKCE verifier, no callback port.
- **Token Rotation Via Upstream**: Two distinct upstream endpoints handle token lifecycle: `POST qwen.aikit.club/v1/validate` (returns the active token, may rotate) and `POST qwen.aikit.club/v1/refresh` (server-side token rotation). The `validate` endpoint may hand back a different token than the one submitted — always use `data.access_token || input_token`, not the input verbatim.
- **Refresh Threshold = 6h Before Expiry**: `qwen-proxy.mjs` refreshes when the token is within 6h of expiry (not at expiry, not 5 min before). Match this window to avoid bursty refreshes.
- **Expiry Leeway = 120s**: `qwen-proxy.mjs` treats tokens as expired 120s before their actual `exp` claim. Use the same leeway to avoid races where the upstream rejects a token we still consider fresh.
- **Trailing `<details>...</details>` Strip Is Mandatory**: Qwen injects a `<details>...</details>` metadata block at the end of response content. The block leaks into Claude Code's UI as visible noise unless stripped. Regex: `/(?:\\n|\n)?<details>[\s\S]*?<\/details>\s*/g`. Apply to both JSON bodies (`response.text().replace(META_RE, '')`) and SSE data lines (only the `data:` payload can contain the block — strip per-line).
- **Endpoint Pairing**: `qwen-auth` is a provider-level transformer (no `endPoint`) — it only handles auth headers and the response strip. The actual `POST /v1/chat/completions` route registration comes from the existing `OpenAI` transformer. Config: `"transformer": { "use": ["qwen-auth", "OpenAI"] }`. Order matters: `qwen-auth` first so the `Authorization` header is set before the request goes out; `OpenAI` second since it has no body logic to disturb the chain.
- **Token File Path Matches Codex Convention**: `~/.claude-code-router/qwen_auth.json` with mode `0o600`. Same security posture as `codex_auth.json` — server and CLI both read/write the same path, no cross-process IPC needed.
- **Auth Page Is Server-Hosted, Not Bookmarklet**: Unlike codex's OAuth redirect, the Qwen auth UX is a plain HTML form served by the running CCR server at `/qwen/auth`. The CLI just prints the URL and reads the local file after the user confirms via Enter. The CLI never makes an HTTP call to the CCR server during auth, so no `APIKEY` is required — the `/qwen/*` routes must be whitelisted in `packages/server/src/middleware/auth.ts`.

## LLM Provider Integration (Cursor SDK)
- **`SDKCustomToolContext.toolCallId` is two ids joined by a newline**: Cursor supplies `call-<uuid>-<n>\nfc_<uuid>_<n>` — the upstream OpenAI-format call id concatenated with the SDK's own tracking id. Anthropic validates `tool_use.id` against `^[a-zA-Z0-9_-]+$` and rejects the *entire* request with `invalid_request_error`, so one bad id fails every later turn. Sanitize at `tools.ts` where the id is consumed, but note that fixing the source is not sufficient: Claude Code replays the full transcript each turn, so ids minted before the fix keep arriving and existing conversations stay permanently broken. The repair must also run in the request direction (`transformRequestOut` + `buildAnthropicBody`), which means the sanitizer has to be **idempotent** and applied to `tool_use.id` and `tool_result.tool_use_id` alike — sanitizing one side of the pair orphans it, which is also a 400. Collapse invalid runs to `_` rather than deleting them: deletion maps `a\nb` and `ab` onto the same id, and a duplicate `tool_use.id` mispairs results silently, which is worse than the error being fixed. Guarded by `cursor-sdk.tool-call-id.ts` and `anthropic.tool-call-id-sanitize.ts`.
- **Propagate asynchronous SDK failures as Anthropic SSE errors**: Cursor can accept agent creation and fail only after the HTTP 200 SSE response has started, for example when account usage is exhausted. Do not run the normal fallback `message_delta`/`message_stop` close path when the upstream stream reader rejects; emit an Anthropic `event: error` with the provider message and end the stream. Otherwise Claude Code treats a real provider failure as an empty successful turn.
- **Recover progress-only terminal turns at the session boundary**: Cursor/Grok can put the substantive result in hidden thinking, publish only a preamble such as “Checking the commit…”, and then report `FINISHED`. Drain the SDK iterator before treating the run as complete, then narrowly detect a short progress-only public message and continue the same agent once inside the still-open client stream. Never retry plan/agent mode, a turn that emitted a host tool, a multi-paragraph response, or a second time.
- **Cursor has no preflight token-count endpoint**: The Cloud Agents API exposes `GET /v1/models` for IDs/variants and `GET /v1/agents/{id}/usage` for post-run usage, but neither tokenizer metadata nor a pre-request count operation. CCR must estimate Claude Code's `/count_tokens` request locally. Missing provider tokenizer configuration is therefore a normal fallback condition and should be logged at debug level, not warning level.
- **Thinking blocks require a closing signature**: Cursor SDK `thinking` messages contain text but no provider signature. Emitting only Anthropic `thinking_delta` events can put the reasoning bytes on the wire while Claude Code never surfaces the block. Before text, tool use, or turn end, emit a separate Unified `delta.thinking.signature` chunk so `AnthropicTransformer` produces `signature_delta` before `content_block_stop`; retain a non-empty synthetic signature in non-stream completions for replay.
- **Cursor thinking has two SDK surfaces**: Some Cursor runs expose reasoning as legacy `run.stream()` `thinking` messages, while token-level reasoning is delivered through `Agent.send({ onDelta })` `thinking-delta` updates. Subscribe to both and tag callback deltas with the active run token; clear queued deltas on cancel/invalidate so an interrupted run cannot leak hidden reasoning into the next Claude Code turn.
- **Transport and display are separate for Claude Code thinking**: Claude Code 2.1.89+ defaults interactive thinking summaries off. Before changing provider or transformer code, correlate upstream thinking deltas, downstream Anthropic SSE, and the Claude Code transcript. If all three contain identical thinking, enable `"showThinkingSummaries": true` in the client settings; the missing terminal output is a client render policy, not a transport failure.
- **Per-request usage, not Cursor cumulative**: `@cursor/sdk` emits `usage` only at true turn end, and `run.usage` / SDK `TokenUsage` are cumulative across the held-open agent session. Parking `customTools.execute` for Claude Code finishes the CCR SSE turn *before* that event, so finish chunks had `usage: null` → Anthropic `message_delta.input_tokens: 0`. End-of-turn finishes that *did* get SDK totals (hundreds of thousands) poisoned Claude Code context accounting.
  - **Fix**: Mirror cursor-opencode-provider — estimate host-facing usage with `chars/4` from the current CCR request (messages + tools) and this turn's emitted text/thinking/tool args. Keep raw SDK totals out of OpenAI/Anthropic request usage, but derive a bounded cache-read ratio from SDK usage deltas so Claude Code can see native Cursor cache hits without inheriting cumulative token totals.
  - **Symptoms**: Claude Code context % stuck near empty during tool loops, or suddenly jumps to absurd values on `end_turn` after a long Cursor session. Inspect `cursor-sdk` finish chunks for missing `usage` or huge `prompt_tokens` that dwarf the Claude Code transcript.
- **Interrupted Cursor runs must not own the next request**: When Claude Code stops a response, the Anthropic wrapper must **return/await** `upstreamReader.cancel(reason)`; otherwise re-entry can overtake `run.cancel()` / iterator teardown. Detach and poison every retiring session before awaiting both cancellation operations concurrently; serialize distinct same-key cleanup, replacement creation, and turn admission so late producers or older concurrent admissions cannot invert ownership. Tag mutable run state with an ownership token. Classify the last Anthropic user block once into request-local structured intent: exact allowlisted interruption-marker text is synthetic only beside a `tool_result`; the same standalone/embedded text, images, and other content are meaningful steering. Do not recover this protocol state later with prompt regexes or leak it into the Unified wire body. A live parked run resumes only for an exact, complete tool-result ID match with no steering; mixed, unmatched, dead, cancelled, or divergent state is retired and full-replayed. Keep the single outstanding Cursor `iterator.next()` on the session across HTTP tool boundaries, and coalesce identical retries behind one bounded response fan-out/replay producer—two responses must never read the iterator independently. Commit a canonical hash of the host-visible request plus the assistant text/tool calls actually emitted; allow a slim same-agent tail send only when model/mode/workspace/guidance/tools still match and the suffix is exactly one supported user message. Cursor's `local.force` bypass is not an alignment proof and must not be used for recovery. Guarded by `anthropic.turn-intent.ts`, `anthropic.stream-cancel.ts`, `cursor-sdk.cancel.ts`, `cursor-sdk.interrupt-reentry.ts`, `cursor-sdk.lifecycle-planner.ts`, `cursor-sdk.turn-coordination.ts`, and `cursor-sdk.turn-identity.ts`.
- **The sandbox workspace reads as the project unless the topology is stated**: Cursor builds its harness prompt server-side from the SDK's workspace root, so the model is told *at system level* that its workspace is `~/.claude-code-router/cursor-sdk-workspaces/<key>`. In Docker that claim is self-consistent (Linux, `/root/…`, empty dir) while Claude Code's real `<env>` block — darwin, the host project root — is demoted into flattened user text by `toSdkPrompt`. Strict system-primacy models (GLM) resolve the conflict toward the sandbox and start prefixing host tool paths with the workspace or refusing to leave it; Cursor-native models (Composer, Grok) ignore the stale root and are unaffected, so a working model proves nothing here. Negating the cwd ("do not treat as the user project") is too weak — state the actual topology: **tools execute on a different machine**, the local FS is empty scratch, and the host project root is `<extracted from the request>`. Deliver it through all three channels Cursor honours: `AGENTS.md` in the workspace (its project-rules channel, injected above user text), the head *and* tail of the flattened prompt, and the deny-hook `agentMessage` (a denied built-in is exactly where the confinement belief forms). Host facts come from `extractHostEnvironment` parsing the `<env>` block per turn; never guess a root when the block is absent. Guarded by `cursor-sdk.host-env.ts`.
  - **Cursor loads workspace rules once per session**: `LocalCursorRulesService` assigns `this._rules = this.load(...)` in its constructor and re-reads only through an optional file watcher, which is not active in the headless local runtime — a canary line appended to a live session's `AGENTS.md` was invisible to the model on the next turn. Rewriting `AGENTS.md` mid-session therefore serves the *next* agent for that directory, not the current one; anything a live turn must see has to travel in the prompt. Note also that rules load from the workspace **and all ancestor directories**, so a stray `AGENTS.md` above `~/.claude-code-router/` would be picked up too.
  - **Detect the symptom, not just the belief**: Prompt guidance is preventive and unverifiable in production. The observable failure is a *host* tool call whose arguments reference the scratch workspace, which otherwise flows through `parkHostTool` looking healthy. Check every custom tool's arguments (recursively, and with `includes` not `startsWith` — shell commands arrive as one string like `cd <workspace> && ls`), return a corrective tool result instead of forwarding, and count it. Cap corrections per session (3) so an explicit user request about that path cannot loop; skip detection entirely when the host root legitimately lives under the scratch root. The per-call `warn` plus per-turn summary is what makes "model X is confined, model Y is not" a metric instead of an anecdote. Guarded by `cursor-sdk.scratch-paths.ts`.
  - **Per-turn tool metrics cannot be a delta over session counters**: `@cursor/sdk` may invoke `customTools.execute` as soon as `agent.send` resolves — before `runCursor` builds the response `ReadableStream`. A baseline captured at stream construction therefore already includes the turn's first violation, and the end-of-turn delta reports `0`. Verified live: the per-call warn fired while the per-turn summary never did. Count per-request state in an object created before the first `send` and passed into `toCustomTools`; that is also immune to mid-request session replacement (fresh-session retry resets session metrics).
  - **A bridge turn's normal exit is the early return, not the end of the loop**: `runCursor`'s stream emits parked host tool calls, calls `controller.close()`, and `return`s from `start()` (`runner.ts`, `event.kind === "host_tool"`). Any end-of-turn reporting placed after the stream loop therefore never runs for the common case — only for turns that end without a tool call. Put it in a `finally` on `start()`'s try/catch so cancels and errors are covered too. Both this and the delta bug were invisible to unit tests and only showed up in live traffic; `cursor-sdk.scratch-report.ts` now reproduces the exact ordering (execute fired inside `send`, turn ended via tool emission) and fails against either regression.
  - **Scratch workspaces are per-session garbage and must be collected**: `dispose()` closed the agent but left the directory, so `~/.claude-code-router/cursor-sdk-workspaces/` grew one directory per session forever — on the volume mounted into the container. Remove on dispose and sweep orphans (>24 h, hourly) for what crashes leave behind. Every removal must be guarded by "direct child of the workspaces root **and** 32-hex-char session key name": `cursorMode: "agent"` can point a session at a user-supplied `cursorCwd`, and that must never be swept.
  - **Never point `cursorCwd` at the host project root from a container**: `ensureWorkspace` calls `mkdirSync(recursive)`, so it would silently create a phantom empty directory at the host path inside the container — an environment that *exists*, is *empty*, and *matches* the real path. That is worse than the mismatch it tries to fix.
  - **Session invalidation is part of cancellation**: Bounded cancellation alone can still leave Cursor's local agent store in an active-run state. If a stopped/failed stream or timed-out cancel makes the session unsafe, poison and remove that SDK agent from the manager. On the next request create a fresh agent and send the full Claude Code transcript; for active-run send failures, first try Cursor's native `local.force` retry, then fresh replay only for an existing session before any new stream is exposed.
  - **A promise held across a generator's early return needs its handler at creation**: `streamSessionEvents` stores the outstanding `iterator.next()` on the session and only attaches a handler when it later races it. Both early-return paths — client abort and a run-token change from a concurrent retirement — return *before* that race, and `run.cancel()` then rejects the orphan with the SDK's internal `AbortError`. Production symptom is the pair `unhandledRejection: AbortError` followed by `PromiseRejectionHandledWarning`, the second warning coming from `cancelActiveRun`'s `void pendingNext?.catch()` attaching one tick too late. Attach `void p.catch(() => undefined)` at every `iterator.next()` site; racing or awaiting the same promise afterwards still works, since a catch does not consume it. The general rule: a promise that outlives the scope that created it must be made handled where it is created, not where it is eventually consumed. Guarded by `cursor-sdk.pending-next-rejection.ts`.
  - **Cursor's synchronous `SDKAgent.close()` does not await executor release**: In `@cursor/sdk` 1.0.23/1.0.24, `close(): void` calls the async `releaseExecutorLease()` without observing its promise. Retiring an already-finished agent can therefore produce the same `AbortError` / late-handled warning even when no `iterator.next()` remains; the production signature is an unhandled rejection immediately after `cursor-sdk session invalidated`, often while the replacement agent is being created. Use the SDK's canonical `await agent[Symbol.asyncDispose]()` behind a bounded, caught disposal helper, and keep that await inside the retirement barrier so replacement creation cannot overtake executor teardown. Guarded by `cursor-sdk.cancel.ts`.
  - **Substring error matchers must be anchored to the phrase that carries the meaning**: `isCursorAgentBusyError` matched bare `"active run"`, which also matches `"no active run"`; `isCursorSendPoisonError` matched bare `"network"`, which matches `"Failed to access network filesystem path"` — a tool result, not a transport failure. Both gate retire-and-replay, so a false positive silently discards a healthy session and full-replays the transcript. Match the SDK's actual phrasing (`"already has active run"`) and enumerate real transport phrases rather than the bare noun. Negative cases belong in the test alongside the positive ones.
  - **Every fallback path must reach the same verdict as the structured one**: `analyzeTrailingCursorToolTurn` trusts `turnIntent` when the Anthropic transformer supplied context, and otherwise re-derives intent from already-flattened Unified messages. `hasMeaningfulUserContent` had no synthetic-marker awareness, so the fallback classified Claude Code's interruption marker as steering and degraded a resume-parked plan into a full retire-and-replay — contradicting the contract documented on `TrailingCursorToolTurn` a few lines above it. When intent is recovered in two places, the weaker path is the one that will run in production during any context-propagation gap. Guarded by `cursor-sdk.trailing-turn-fallback.ts`.

## LLM Provider Integration (Antigravity)
- **Server must import Antigravity helpers from core, not reimplement them**: CLI may ship independently and therefore keeps its own `packages/cli/src/utils/antigravity-auth.ts` copy. `packages/server` already depends on `@caeliq/llms`, so OAuth callback routes must use core's `exchangeAuthorizationCode` / `fetchUserEmail` / `resolveProjectId` / `saveTokens`. A local reimplementation drifted (missing Antigravity client headers on `pollOnboardOperation`) and can fail project discovery mid-onboard. Export the helpers from `packages/core/src/server.ts` so they ship through the generated `@caeliq/llms` typings (`packages/core/dist/*.d.ts`); do not reintroduce a manual `packages/server/src/types.d.ts` shim.
- **Save tokens before `resolveProjectId` in the OAuth callback**: `resolveProjectId` falls back to `loadTokens().project_id`. If the auth file still holds a previous account's project id when discovery runs, the callback can stick to the stale project. Persist the new tokens first (optionally with verifier `project_id`), then call `resolveProjectId` so discovery sees the fresh file.

## Development & Tooling
- **Dependency Scoping**: `pino` is provided by Fastify in the server package but is not a direct dependency of the `core` package. Direct imports of `pino` in `core` will cause build failures; use the passed-in `logger` instance or native `fs` for separate log files.
- **Core Type Check Includes Test Scripts**: `packages/core/tsconfig.json` includes `src/**/*`, so test-only scripts must type-check under the core compiler options even if they run via `tsx`. Avoid top-level `await` and `import.meta` in these scripts unless the package tsconfig changes; use an async `main()` and runtime-safe path discovery instead.
- **Response Cloning**: When implementing background logging for responses, use `response.clone()` to avoid consuming the original stream, which would otherwise prevent the transformer from processing the output.
